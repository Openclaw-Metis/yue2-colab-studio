# 已知問題與限制

更新日期：2026-11-11

## 尚未在 Colab L4 上驗證

| 現象 | 原因 | 暫時作法 |
|---|---|---|
| 沒有任何 L4 實測結果 | 開發階段只在 Windows 上以替身引擎測試，沒有執行真正的 YuE2 | 依 `colab-manual-checklist.md` 執行並回填。在那之前，請把本專案視為「程式完成、未經實機驗證」 |
| 第一格可能在安裝或 `pip check` 失敗 | `gradio==6.17.3` 與 YuE2 釘死的 `huggingface-hub==0.36.2`、`numpy==2.2.6` 的相容性只在 Windows、Python 3.13 上解析過；Colab 預裝套件也可能與釘死版本衝突 | 保留完整輸出。若是 Gradio 造成，改用可相容的版本並更新 `requirements-colab.txt` |
| L4 可能記憶體不足 | 官方建議 24 GB，L4 回報約 22.5 GB。官方在 RTX 4090 的實測峰值是 14.08 GiB，推斷可行但未實測 | 在 `engine.py` 的 `from_pretrained` 傳入較低的 `memory_budget_gib`，或加上 `low_vram=True`（會變慢） |
| 生成時間未知 | 官方沒有 L4 數據 | `colab-baseline.md` 量測後回填。逾時門檻 45 分鐘是暫定值 |
| `nvidia-smi --query-gpu=compute_cap` 在 Colab 的驅動是否可用未確認 | 欄位需要較新的驅動 | 失敗時會退回以 GPU 名稱判斷（L4、A100、T4 等已知型號） |

## Colab 本身的限制

| 現象 | 原因 | 暫時作法 |
|---|---|---|
| 選不到 L4 | Colab 不保證分配，且需要運算單元 | 稍後再試 |
| 閒置或長時間執行後斷線 | Colab 的使用政策 | 重要的歌先下載；或使用 Google 雲端硬碟保存 |
| 執行階段被回收後歌曲消失 | 預設保存在 `/content` | 第二格勾選 `USE_DRIVE` |
| `gradio.live` 連結打不開 | 分享通道服務中斷，或被網路服務商封鎖 | 稍後重新執行第三格 |
| 每次開新的執行階段都要重新下載權重 | 權重快取在 `/content/hf_cache`，刻意不放 Drive（檔案大、讀取慢） | 無 |

## 設計上的限制

| 現象 | 原因 |
|---|---|
| 相同的隨機種子不保證做出相同的歌 | 上游文件說明不同 GPU、執行環境與注意力核心都會改變結果 |
| 先產生樂譜再生成，和直接生成的結果可能不同 | 兩條路徑的取樣過程不同 |
| 沒有歌曲長度、調性、BPM 的獨立欄位 | 上游請求沒有這些欄位；要寫在曲風文字或樂譜裡 |
| 歌詞留空不保證沒有人聲 | 上游文件明示 |
| 樂譜只有 Vocal 與 Ins 兩個聲部有作用 | 上游文件明示；多餘聲部會原樣送出但不會成為獨立控制 |
| 改樂譜會重新生成整首歌 | 上游是重新生成，不是局部修改波形 |
| 解碼與保存階段不能取消 | 上游在 VAE 解碼開始後不再檢查取消 |
| 同時只能有一個工作、一個使用者 | 上游一次處理一首；本專案是單人工具 |
| 兩個瀏覽器分頁同時編輯時草稿以最後寫入為準 | 沒有做多分頁同步 |
| 樂譜格式沒有在送出前做語法檢查 | 上游的請求前置檢查只驗欄位，不解析 ABC；錯誤會在生成時回報為「樂譜格式有問題」 |

## Gradio 6.17.3 的觀察

2026-11-11 以內建瀏覽器自動化測試時觀察到，尚未以手動鍵盤輸入交叉確認：

| 現象 | 因應 |
|---|---|
| Textbox 的 `.input` 事件在輸入文字時沒有觸發，`.change` 會觸發 | 全部改用 `.change`。因為 `.change` 也會被程式設定的值觸發，綁在表單欄位上的處理函式不可回寫表單欄位 |
| Dataframe 的 `select` 事件沒有進到處理函式 | 歌曲庫改用單選清單 |
| 瀏覽器偏好深色時會套用深色主題 | 以 `head` 內的腳本加上 `?__theme=light` |
